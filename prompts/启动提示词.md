## 每个任务的固定动作

1. 从看板取编号最小的 `TODO` 任务，改成 `DOING`
2. 先读该任务列出的现有文件，理解当前实现
3. 切分支 `feat/T<编号>-<简述>`
4. 写测试 → 此时应当失败 → 提交 `test(...)`
5. 写最小实现 → 提交 `feat(...)`
6. 补边界情况、重构 → 提交 `refactor(...)` 或 `fix(...)`
7. 跑验收：`./mvnw -B -ntp verify`、`cd frontend && npm test && npm run build && npm run format:check`；涉及接口或业务流的再跑冒烟
8. 逐条核对 `AGENTS.md` §4.1 的七条 DoD
9. 更新 `docs/进度看板.md`：状态改 `DONE`，填实际行数与提交数，记一行每日记录，然后提交 `docs(...)`
10. 按下面的格式汇报，接着做下一个任务

## 五条不可协商

1. **测试必须你自己跑。** 汇报时粘贴原始输出行，例如 `Tests run: 24, Failures: 0, Errors: 0, Skipped: 0`。不许说"测试应该可以通过"。
2. **禁止让测试变绿的作弊手段**：`@Disabled`、`-DskipTests`、`|| true`、`catch (Exception e) {}`、把断言改成恒真、注释掉失败用例。`Skipped` 不为 0 视为任务未完成。
3. **禁止碰兼容性红线**：不改 `V1__create_travel_schema.sql`；接口只增不改；新增列必须可空或有默认值；`image_key` 必须保留并作为回退；不引入 ORM、UI 框架、图表库。
4. **一次只做一个任务。** 做完、测试绿、看板更新，再开下一个。不要同时铺三个功能。
5. **同一个问题连续两次修复失败就停。** 把失败命令、完整报错、已尝试的方案写清楚，标记 `BLOCKED`，然后停下等我介入。不要换个写法硬凑，更不要降低验收标准。
